# Game Cube Go — план развития и будущие версии

# Цель документа

Этот документ фиксирует порядок разработки Game Cube Go. Он не отменяет полный набор требований к будущей версии игры, а определяет, в каком порядке функциональность вводится, чтобы как можно быстрее получить первую полностью играбельную и хорошо протестированную версию, а затем двигаться небольшими независимыми шагами. По вопросу о том, в какой версии появляется конкретная функция, этот roadmap является источником истины; основной документ «Game Cube Go» определяет подробное поведение функции после того, как соответствующий этап уже введён. Нормативная нумерация текущего roadmap: 0.1 — Torus 2D; 0.2 — Cube 2D; 0.3 — Automatic/Assisted alive/dead/seki; 0.5 — Cube 3D. Версия 0.4 сознательно отсутствует: прежний этап Advanced/Branching History удалён из roadmap, а линейный Undo/Redo закреплён как окончательная пользовательская модель истории уже в 0.1. Старую схему «0.3 \= Cube 3D» считать отменённой и не использовать ни в ТЗ, ни в архитектуре, ни в документации к коду.

# Основной принцип

Игровой движок, топология поля и отображение должны быть разделены. Движок не должен зависеть ни от тора, ни от куба, ни от 2D/3D. Он работает с логическими точками и их соседями. Поэтому TorusTopology, CubeTopology, Renderer2D и Renderer3D должны подключаться как отдельные слои. Это позволит ранним версиям не превращаться в выброшенные прототипы.  
Дополнительно первая версия должна быть архитектурно готова к возможному онлайн-режиму, но не реализовывать его. Game Engine работает только с сериализуемым GameState и доменными командами; UI не меняет игровое состояние напрямую, сохранение подключается через репозиторий, а модель игрока допускает позднюю привязку аккаунта. GameState содержит только данные, влияющие на правила и точное воспроизведение партии; визуальное состояние хранится отдельно в ViewState и не может влиять на Game Engine. Стадия партии задаётся одной явной state machine, а не набором противоречивых флагов. Движок не зависит от браузера, DOM, рендеринга, ViewState или localStorage и должен быть пригоден для запуска без UI, в том числе в будущем на сервере. Сетевой транспорт, аккаунты и серверная инфраструктура остаются отдельными будущими слоями.

# Версия 0.1 — Torus 2D: первая полностью играбельная версия

Цель: как можно быстрее получить игру, в которую можно сыграть полноценную партию от первого хода до определения победителя.

## Входит в версию:

* Тороидальная 2D-топология: переход справа налево и сверху вниз, у каждой точки четыре различных логических соседа. Доступные размеры тора уже в 0.1: 9×9, 13×13 и 19×19; если для тора ещё нет сохранённого выбора, начальный размер — 9×9. Уже в 0.1 TorusTopology обязана проходить универсальный Topology Contract: отсутствие self-links, симметричность соседства, связность графа и стабильность PointId.  
* Базовая механика ГО: постановка камней, группы, дыхания, взятия, запрет самоубийства, обычное ко, чередование игроков и пас.  
* Два переключаемых режима правил/финального подсчёта уже в первой версии: китайский area scoring и японский territory scoring; коми поддерживается в обоих режимах. Перед началом новой партии пользователь выбирает «Японские» или «Китайские»; Japanese показываются первыми и выбраны по умолчанию для каждой новой партии, коми по умолчанию — 7.5. В 0.1 базовая механика хода для обоих вариантов общая — группы, дыхания, взятия, запрет самоубийства, ko/repetition, чередование и пасы работают через один Game Engine; переключение выбирает соответствующую scoring/endgame policy, а будущие дополнительные различия правил при необходимости добавляются отдельной RulePolicy.  
* После двух последовательных пасов игровая фаза завершается и партия переходит из PLAYING в ENDGAME\_REVIEW. После обязательной финальной классификации создаётся resolvedLifeDeathResult, выполняется подсчёт по выбранному набору правил и партия переходит в FINISHED.  
* Финальная классификация групп на этом этапе выполняется вручную пользователем. В версиях 0.1–0.2 автоматическая классификация отсутствует: пользователь работает прямо с группами на доске и назначает им один из трёх явных статусов — alive, dead или seki; повторная классификация разрешена. Маркировка проводится линиями через центры камней толщиной 4 px: dead — красная, seki — серая, alive — в цвет камней. Ответ пользователя является источником истины для итогового подсчёта; автоматическое распознавание откладывается до 0.3. После расчёта финальная территория остаётся видна на доске: территория чёрных затемняется примерно на 20%, белых высветляется примерно на 20%, neutral не меняется, dead stones заметно приглушаются. Окно результата оформляется в том же тёмном стиле и после закрытия не убирает финальную визуализацию.  
* Линейная история уже в 0.1 поддерживает Undo и Redo. Undo точно откатывает последнее действие, включая Pass и переход в ENDGAME\_REVIEW/FINISHED; Redo возвращает отменённое действие и всё связанное состояние. После Undo любое новое принятое игровое действие очищает redo-будущее.  
* Локальное автосохранение текущей партии в браузере.  
* Базовый законченный интерфейс, достаточный для нормальной игры. Уже в 0.1 основной игровой layout использует компактную служебную панель слева примерно на 20% доступной ширины и игровую область с доской справа примерно на 80%, с аккуратным отступом между ними; фон игрового окна — \#04090f. В левой панели находятся current turn, размер поля, номер хода, правила, komi, счётчики «Black Captured»/«White Captured», display options и игровые действия. Отдельную строку «Passes» в статистическом блоке не показывать: после первого паса состояние видно по подписи «Pass (1)». Над доской не должно быть служебных заголовков/версий/строк состояния — только элементы, непосредственно управляющие полем.  
* Автоматические тесты движка и сценарные тесты полной партии. Уже в 0.1 вводятся unit-тесты, базовые property-based/fuzz-проверки инвариантов и внутренний fixture-формат эталонных позиций для TorusTopology.  
* Актуальный visual/input polish Torus 2D 0.1: обычный курсор мыши остаётся видимым; допустимое наведение показывает полноценный SVG-камень текущего цвета с opacity 50%, привязанный к ближайшему пересечению; запрещённый ход показывает красный marker точно в запрещённом пересечении. Навигационные стрелки физически сдвигают сетку и камни с бесшовным wrap примерно за 240 мс. Опция «Show duplicate regions» показывает только одну пунктирную неинтерактивную обёрнутую строку/колонку у каждого края, а не четыре; edge-копии камней приглушены примерно до 50%. «Move numbers» и «Show duplicate regions» расположены вертикально, в таком порядке. Доска использует wood texture board-bg.jpg, тёмный фон приложения виден вокруг неё; сетка ориентировочно 2 px на 9×9, 1.5 px на 13×13 и 0.8 px на 19×19. Последний камень имеет контрастную центральную точку, номера ходов учитывают пропуски от Pass и снятых камней. Обычная постановка получает мягкую animation около 100 мс. Снятые белые камни летят влево, снятые чёрные — вправо с небольшим уклоном вверх, независимо от layout панелей; группа стартует последовательно примерно через 150 мс.  
* Архитектура управления через доменные команды и сериализуемый GameState с версией схемы: UI формирует PlaceStone/Pass/Undo/Redo и другие команды, а Game Engine является единственным слоем, который создаёт новое игровое состояние. GameState и ViewState разделены: камера, зум, панорамирование, центральная доска, режим отображения и другие визуальные параметры не входят в игровое состояние и не участвуют в правилах, scoring или истории ходов.  
* Абстракция хранения GameRepository или эквивалент: в версии 0.1 реализуется только LocalGameRepository; модель партии также содержит абстрактные PlayerSlot с внутренними id и цветом без регистрации и аккаунтов.  
* Headless-тесты Game Engine без UI: полную партию можно прогнать командами напрямую, включая Undo/Redo, сериализовать состояние, восстановить его и получить тот же результат без зависимости от браузера и визуальных модулей.  
* Pass UX в 0.1: после первого Pass кнопка показывает «Pass (1)» и примерно на 1 секунду блокирует только повторный Pass. Видимого progress/countdown и отдельной надписи о предыдущем пасе нет; обычный ход разрешён сразу и сбрасывает последовательность пасов. Pass, Undo, Redo и New Game должны иметь одинаковую высоту; активные Undo/Redo получают тонкую светло-жёлтую обводку. Выбор 9×9/13×13/19×19 в New Game оформляется отдельными кнопками, а не выпадающим списком.  
* Developer/debug renderer или эквивалентный служебный режим создаётся уже в 0.1 и может показывать PointId, соседей, id групп, дыхания, связные пустые области и другие диагностические данные. Он не является пользовательской функцией и не должен попадать в обычный игровой интерфейс.

## Не входит в версию:

* Кубическая топология.  
* Любой 3D-режим.  
* Автоматическое определение мёртвых групп.  
* 3D-тор.  
* Сервер, регистрация и логин, база пользователей, облачное хранение, API/WebSocket, сетевые матчи, лобби, приглашения, матчмейкинг, рейтинг, друзья, reconnect, наблюдатели и античит.

Критерий готовности: несколько полных партий на торе проходят от начала до конца в обоих режимах — «Китайские» и «Японские»; ручная классификация alive/dead/seki, правила, Undo/Redo, Pass, сохранение, one-line duplicate edge strips, hover/forbidden preview и оба варианта итогового подсчёта покрыты тестами; TorusTopology полностью проходит Topology Contract; базовый fixture-набор и property-based/fuzz-проверки проходят стабильно; сериализация GameState детерминированна, а ViewState не влияет на игровой результат.

# Версия 0.2 — Cube 2D

Цель: добавить настоящую CubeTopology рядом с уже работающей TorusTopology, сохранив проверенный игровой движок и не удаляя торический режим.

## Входит в версию:

* CubeTopology с шестью досками и корректными переходами через рёбра и углы должна быть параметризована размером N×N и не зависеть от заранее зафиксированного списка размеров. Начиная с 0.2 перед новой партией доступен выбор топологии двумя равноправными selectable controls с видимыми подписями «Cube» и «Torus»: рядом с «Cube» показывается маленькая иконка куба, рядом с «Torus» — маленькая иконка тора/кольца, визуально похожая на бублик. Иконка и подпись образуют одну кликабельную область; иконки должны быть лёгкими, предпочтительно SVG, и выполнены в общем стиле интерфейса. Рабочий первоначальный UI-набор Cube 2D может включать 2×2, 3×3, 4×4 и 5×5, но этот список является предварительным, а не архитектурным ограничением и может быть изменён после игрового тестирования. Добавление 6×6, 8×8, 10×10 или другого разумного N не должно требовать изменения Game Engine или фундаментальной логики CubeTopology. Для Torus сохраняются 9×9, 13×13 и 19×19. По умолчанию при первом выборе в 0.2 используется Cube; TorusTopology продолжает поддерживаться тем же Game Engine.  
* Ровно четыре различных логических соседа у каждой игровой точки. CubeTopology обязана пройти тот же универсальный Topology Contract, который уже применяется к TorusTopology в 0.1; в 0.2 контракт расширяется кубическими проверками согласованности переходов через каждое ребро и угол, не создавая отдельного набора фундаментальных правил для куба.  
* Cube 2D всегда отображает ровно шесть физических граней куба, каждую ровно один раз. Экранная модель использует матрицу 4×3 как набор из 12 возможных layout slots: заняты ровно 6 позиций, остальные 6 пусты. Начальная раскладка: row 0 — empty / TOP / empty / empty; row 1 — LEFT / CENTER / RIGHT / BACK; row 2 — empty / BOTTOM / empty / empty. TOP и BOTTOM образуют одну визуальную вертикальную пару, которую пользователь может переносить вместе между четырьмя колонками 0–3 кликом по пустому slot сверху или снизу соответствующей боковой доски. Выбранная колонка хранится только во ViewState как verticalAnchorColumn и не меняет GameState или CubeTopology. При переносе пара пересчитывает свои CubeFace/rotation относительно боковой доски выбранной колонки, поэтому реальные стыки сохраняются. Пустой slot не является доской, logical PointId или игровым hit target для постановки камня; его кликабельность используется только как UI-control перестройки layout. При hover такой slot обозначается тонкой пунктирной рамкой. Никаких визуальных дублей граней или logical PointId в Cube 2D нет; общее число отображаемых игровых точек всегда равно 6 × N × N. Cube 2D обязан визуально продолжать утверждённый Torus 2D: использовать общий BoardTheme, ту же фактуру/цвет доски, те же SVG чёрного и белого камня и их highlight/shadow semantics, тот же характер сетки, hover-preview, last-move marker, move numbers, forbidden marker, endgame alive/dead/seki annotation и финальную territory/dead-stone визуализацию. Отличаться могут только геометрия, размеры/толщина сетки по необходимости, расположение шести уникальных граней, стыки, повороты и навигация.  
* Каждая CubeFace и каждая её logical PointId имеют ровно одно визуальное представление в текущем Cube 2D layout; renderer не создаёт duplicate cells, duplicate boards или duplicate hit targets.  
* Навигация Cube 2D использует те же шесть уникальных граней без постоянных дублей. Горизонтальные команды moveLeft()/moveRight() образуют бесконечную циклическую галерею четырёх боковых граней LEFT/CENTER/RIGHT/BACK: ряд плавно сдвигается на одну доску, крайняя грань уходит за край, а продолжение четырёхгранного цикла входит с противоположной стороны; после transition снова видны те же четыре уникальные боковые CubeFace. Отдельно от стрелочной навигации пользователь может кликом по пустому slot в верхней или нижней строке выбрать verticalAnchorColumn 0–3: TOP/BOTTOM как единая визуальная пара переезжают в эту колонку и получают face/rotation относительно соответствующей боковой доски. Это действие меняет только ViewState/layout и не меняет CubeOrientation, CENTER или GameState. При последующей горизонтальной навигации выбранная колонка сохраняется, а содержимое пары пересчитывается для нового side ring. Вертикальные moveUp()/moveDown() по-прежнему меняют текущую CENTER через CubeOrientation и пересобирают layout; это отдельное действие от клика по пустому slot. Временный animation-only clone допустим только для бесшовного горизонтального wrap, не входит в Cube2DLayout и не имеет игрового hit target. Актуальная последовательность внутренних задач 0.2: 01.01 CubeTopology остаётся без изменений; 01.02.1 корректирует Cube2DLayout, сохраняя CubeOrientation, rotation и presentation-only verticalAnchorColumn; 01.03 создаёт renderer поверх исправленного layout; 01.04 реализует горизонтальную галерею, вертикальную перестройку и перенос TOP/BOTTOM по пустым layout slots.  
* Оба набора правил/подсчёта — ChineseScoring и JapaneseScoring, а также ручная классификация alive/dead/seki, сохранение и история продолжают работать через тот же Game Engine без отдельной кубической версии правил.  
* Существующие с 0.1 Topology Contract, property-based/fuzz-проверки и fixture-формат расширяются кубическими сценариями. Библиотека должна покрывать каждое ребро и угол, взятия, ко, группы, глаза и пустые области, пересекающие границы досок, а также контракт Cube2DLayout: в каждом стабильном состоянии матрица 4×3 содержит ровно 6 занятых cells, каждая CubeFace ровно один раз, 6 пустых slots и ровно 6 × N × N visual points. Отдельно тестируется verticalAnchorColumn для всех четырёх колонок: клик по любому доступному пустому slot сверху или снизу переносит единую пару TOP/BOTTOM в выбранную колонку, не меняет GameState/CubeOrientation, не создаёт дублей и сохраняет корректные face/rotation и реальные стыки. Пустые anchor-slots могут иметь layout-control hit target, но не имеют logical PointId и не принимают постановку камня. Также отдельно тестируется бесконечная горизонтальная галерея: многократные ←/→ циклически меняют порядок четырёх боковых граней без накопления постоянных копий; после каждого завершённого перехода инвариант шести уникальных граней восстановлен. Параметризованная CubeTopology должна прогоняться на нескольких N, включая чётные и нечётные размеры и как минимум один технический размер вне UI-набора.

Критерий готовности: полноценная партия Cube Go играется в 2D; CubeTopology полностью проходит Topology Contract и доказана как параметризованная N×N без привязки к конкретному UI-набору размеров; результаты движка совпадают с ожидаемыми для всей библиотеки эталонных позиций на рёбрах, углах и стыках досок; выбор «Cube» / «Torus» с соответствующими маленькими иконками работает корректно; Cube 2D использует общий с Torus 2D BoardTheme/shared stone SVG и не создаёт независимую визуальную тему; все regression-тесты Torus 2D из 0.1 продолжают проходить без изменений.

# Версия 0.3 — автоматическая помощь в классификации alive / dead / seki

Цель: после стабилизации настоящей CubeTopology сократить ручную работу при финальном разборе, автоматически распознавая очевидные alive/dead/seki, но сохранить ручную классификацию обязательным fallback для всего, что программа не может доказать однозначно.

## Входит в версию:

* Автоматически определять очевидные живые, мёртвые группы и очевидные случаи сэки.  
* Классификатор работает только через логический граф и интерфейс Topology: он не должен зависеть от плоских координат, конкретной 2D-развёртки, визуальных копий досок или будущего 3D.  
* Не пытаться любой ценой автоматически разрешать спорные позиции: отсутствие доказательства означает необходимость ручного решения, а не автоматическую догадку.  
* Если положение неоднозначно, передавать его пользователю для ручной классификации с тремя вариантами: «живая», «мёртвая» или «сэки», и принимать ответ как окончательный для текущего финального состояния.  
* Сохранить анализ alive/dead/seki отдельным модулем, не влияющим на базовую механику ходов и формулы ChineseScoring/JapaneseScoring.  
* ChineseScoring и JapaneseScoring получают единый resolvedLifeDeathResult независимо от того, был статус определён автоматически или подтверждён пользователем.  
* Эталонные fixture-позиции расширяются случаями alive/dead/seki на рёбрах и углах куба, а также проверочными позициями на торе; один и тот же классификатор обязан работать через обе топологии без специальных кубических или торических веток.

Ручная классификация не удаляется после появления автоматической помощи: она остаётся постоянным механизмом разрешения всех недоказанных или спорных случаев.

Критерий готовности: очевидные alive/dead/seki корректно определяются автоматически на CubeTopology и TorusTopology для обоих режимов подсчёта, а всё недоказанное безошибочно передаётся пользователю на ручную трёхвариантную классификацию.

# Версия 0.5 — Cube 3D

Цель: добавить полноценное трёхмерное представление уже полностью работающей Cube Go, не меняя игровое состояние, правила, историю или алгоритмы анализа позиции.

## План:

* 3D-куб с шестью игровыми гранями и непрерывным визуальным переходом сетки через рёбра; вращение мышью, зум и возврат к стандартному виду.  
* Наведение, hit-testing и постановка камней в 3D должны однозначно сопоставляться с теми же логическими PointId, которые уже используются Cube 2D.  
* Отображение камней, последнего хода, номеров, территории, живых/мёртвых групп и сэки в 3D.  
* Переключение Cube 2D ↔ Cube 3D без изменения GameState, с сохранением понятной ориентации и пространственного якоря между представлениями.  
* Необходимые 3D-анимации и визуальная полировка реализуются только в Renderer3D/визуальном слое и не должны создавать отдельную 3D-версию игровой логики.  
* Chinese/Japanese scoring, auto/manual alive/dead/seki, Undo/Redo и сохранение должны работать в 3D через тот же Game Engine без расхождений с Cube 2D.

Критерий готовности: одну и ту же сохранённую партию можно без расхождений продолжать, анализировать, откатывать и завершать в Cube 2D и Cube 3D; различается только Renderer и способ взаимодействия с представлением.

# Будущая версия — Online Multiplayer (после текущего плана)

Цель: когда локальная игра и игровое ядро станут устойчивыми, добавить аккаунты и сетевые матчи как внешние слои вокруг уже проверенного Game Engine, не переписывая базовую механику ГО.

## Принципы будущей реализации:

* Сервер становится авторитетным источником истины по партии и запускает тот же Game Engine или максимально близкую общую реализацию без зависимости от браузера и рендеринга.  
* Клиент передаёт намерение игрока — например «поставить камень в точку X» или «пас», — а не готовое новое состояние. Сервер самостоятельно проверяет очередь, допустимость хода, ко, самоубийство, взятия и остальные правила.  
* ServerGameRepository добавляется как новая реализация того же интерфейса хранения; локальный репозиторий не удаляется и продолжает обслуживать локальный режим.  
* Аккаунт зарегистрированного пользователя привязывается к уже существующему PlayerSlot, поэтому базовая модель партии не требует переработки.  
* HTTP/API, WebSocket или другой сетевой транспорт только доставляет доменные команды и авторитетные GameState между клиентом и сервером и не входит внутрь Game Engine.  
* Лобби, приглашения, матчмейкинг, рейтинг, друзья, reconnect, наблюдатели, античит и другие сетевые возможности добавляются независимо по мере необходимости; их не нужно проектировать или реализовывать в версиях 0.1, 0.2, 0.3 и 0.5.

Эта будущая версия пока не получает номер и не меняет текущий порядок 0.1 → 0.2 → 0.3 → 0.5. Пропуск 0.4 является сознательным и не означает незаполненный этап. До решения о реальном онлайне мы оплачиваем только небольшую архитектурную подготовку, полезную и для локальной игры.

# Что принципиально откладываем

Версия 0.1 не должна одновременно решать кубическую геометрию, 3D и автоматическое распознавание жизни/смерти/сэки. При этом именно в 0.1 создаются дешёвые универсальные инструменты, которые снижают стоимость следующих этапов: Topology Contract, базовый fixture-формат, property-based/fuzz-проверки, разделение GameState/ViewState, явная state machine стадий партии и служебный debug renderer. Китайский и японский подсчёт, переключение между ними, ручная классификация alive/dead/seki и окончательная линейная модель Undo/Redo также входят уже в 0.1. В 0.2 вводится окончательная CubeTopology и 2D-представление куба. После стабилизации Cube 2D, в 0.3, добавляется автоматическая помощь alive/dead/seki. 3D-куб намеренно откладывается до 0.5. 3D-тор в текущие запланированные версии 0.1, 0.2, 0.3 и 0.5 не входит и может рассматриваться только как отдельная будущая версия.

# Порядок развития

0.1 Torus 2D \+ Chinese/Japanese Scoring \+ Manual alive/dead/seki \+ Undo/Redo \+ universal Topology Contract/Fixtures → 0.2 Cube 2D → 0.3 Automatic Endgame Classification → 0.5 Cube 3D. 0.4 не используется; Cube 3D не относится к 0.3.

Каждая версия должна оставаться рабочей контрольной точкой. Следующий этап начинается только после того, как предыдущий можно нормально сыграть, прогнать через автоматические, property-based/fuzz и fixture-тесты и считать технически устойчивым. Перед началом 0.2 TorusTopology и базовый Game Engine обязаны полностью проходить универсальные контракты. Перед началом 0.3 CubeTopology обязана проходить тот же Topology Contract вместе с кубическими расширениями. Перед началом 0.5 GameState, endgame и окончательная линейная модель Undo/Redo должны быть устойчиво доказаны в Cube 2D.

# Постоянные инженерные правила

Эти правила действуют для всех версий и важнее удобства конкретной реализации.

## Единая панель управления

## Начиная с 0.1 во всех игровых режимах используется один физически общий UI-компонент панели управления — GameControlPanel или эквивалент. Torus 2D, Cube 2D, Cube 3D с 0.5 и любые будущие представления подключают этот же компонент. Отдельные копии панели или независимые Torus/Cube/2D/3D-версии запрещены. Общие данные и действия — current player, move/action number, размер, rules/scoringMode, komi, captures, Pass, Undo, Redo, New Game, display options и будущие общие controls — развиваются в одном месте и получают единый дизайн.

## Режим может через capabilities скрыть неприменимый control или показать предусмотренное disabled-состояние, но не заменяет панель собственной реализацией. Переход между topology/view mode меняет Renderer/представление поля, а не основную панель управления.

## Если для нового режима или функции в общей панели не хватает места, отсутствует необходимая кнопка/control, возникают конфликтующие требования или любая другая причина, из\-за которой одна общая панель перестаёт корректно работать, агент/ChatGPT не должен самостоятельно обходить проблему созданием второй панели, переносом обязательных controls наружу, скрытием обязательной функции, чрезмерным ужатием или отдельной раскладкой только для одного режима.

## **\!\!\! ВНИМАНИЕ: ПРОБЛЕМА С ЕДИНОЙ ПАНЕЛЬЮ УПРАВЛЕНИЯ \!\!\!**

## При таком конфликте агент/ChatGPT обязан до реализации вывести пользователю максимально заметное предупреждение отдельным абзацем, жирным текстом и восклицательными знаками, кратко объяснить проблему и явно запросить продуктово-дизайнерское решение. До решения пользователя архитектура и структура общей панели не меняются, а обходной вариант не внедряется.

## Разделение GameState и ViewState

GameState содержит только данные, способные изменить допустимость ходов, результат, историю или точное воспроизведение партии: топологию, камни, очередь, ко, пасы, пленных, scoringMode, коми, стадию партии, endgame-решения и итог. ViewState содержит только представление: зум, панорамирование, ориентацию камеры, центральную доску, положение 2D-развёртки, включённые визуальные режимы и состояние анимаций. Game Engine не читает ViewState. История игровых действий не должна зависеть от ViewState. При необходимости оба объекта можно сохранять рядом, но они сериализуются и восстанавливаются как разные сущности.

## Явная state machine партии

Стадия партии хранится как одно каноническое состояние, а не как набор независимых boolean-флагов. Базовая схема: PLAYING → ENDGAME\_REVIEW → FINISHED. Второй последовательный пас переводит PLAYING в ENDGAME\_REVIEW; завершение обязательной классификации создаёт resolvedLifeDeathResult и переводит игру в FINISHED. Undo выполняет определённый обратный переход и восстанавливает точное предыдущее состояние; Redo симметрично возвращает отменённый переход, пока redo-будущее не очищено новым игровым действием. Ввод новых стадий в будущем выполняется расширением state machine, а не добавлением несогласованных флагов.

## Property-based и fuzz-тестирование

Помимо заранее известных fixture-позиций движок должен проходить генерируемые последовательности допустимых действий. Проверяются инварианты: детерминированность одинаковых команд из одинакового состояния; точность Undo/Redo; очистка redo-будущего новым действием; эквивалентность serialize → deserialize; отсутствие нелегальных групп без дыханий после завершённого допустимого хода; согласованность количества пленных и истории; сохранение четырёх соседей и других свойств Topology Contract; идентичный результат повторного проигрывания одной последовательности команд. Найденный fuzz-тестом дефект должен превращаться в постоянный минимальный regression fixture.

## Developer/debug renderer

В development-сборке должен существовать служебный диагностический режим, который по запросу показывает PointId, четыре логических соседа, id группы, дыхания, связанные пустые области и другие данные, необходимые для диагностики. Начиная с Cube 2D он также должен показывать CubeFace, role (LEFT/CENTER/RIGHT/BACK/TOP/BOTTOM), row/column slot, rotation и однозначное соответствие visual point → logical PointId; отдельно должно быть видно, что каждая CubeFace присутствует ровно один раз. Визуальные дубли диагностируются только там, где они реально существуют как renderer-only механизм, например в Torus one-line edge strips. Этот режим не является пользовательской функцией и не определяет игровую логику.

## Три внутренних quality gate каждой версии

Каждая пользовательская версия проходит три обязательные внутренние стадии: Core → Functional UI → Polish. На Core реализуется и тестируется логика без зависимости от красивого интерфейса. На Functional UI функция полностью доступна пользователю, но допускает минимальные анимации и временно простой визуал. Только после прохождения функциональных тестов начинается Polish: плавность, анимации, эффекты и визуальная настройка. Визуальная полировка не должна маскировать незаконченный Core и не может быть условием тестирования игровой логики.

## Внутренние технические контрольные точки

Номер пользовательской версии не требуется дробить в публичном интерфейсе, но внутри разработки крупный этап делится на проверяемые checkpoints. Для текущей 0.2 последовательность уточнена: 01.01 CubeTopology остаётся без изменений; 01.02.1 исправляет Cube2DLayout при сохранении CubeOrientation/rotation; 01.03 заново строит Cube2DRenderer поверх исправленного layout и рисует ровно шесть уникальных досок; 01.04 добавляет navigation через moveLeft()/moveRight()/moveUp()/moveDown() → новая CubeOrientation → новый layout тех же шести граней. Cube 3D проходит renderer-core → hit-testing/input → feature-parity with Cube 2D → polish → release. Следующий checkpoint не начинается, пока предыдущий не имеет автоматического критерия готовности.

## Версионная маркировка требований

Каждое новое или изменяемое требование должно иметь introducedIn — минимальную версию, в которой оно обязательно. Если весь раздел вводится одной версией, introducedIn допускается задавать на уровне раздела и наследовать всеми его пунктами; смешанный раздел обязан иметь явные переопределения для требований с другой версией. Подробный документ описывает поведение, roadmap остаётся источником истины по introducedIn. Это правило предназначено прежде всего для предотвращения ситуации, когда агент реализует будущую функцию раньше времени.

## Правило независимой тестируемости слоёв

Если слой невозможно полноценно протестировать без ещё не созданного следующего слоя, граница архитектуры считается подозрительной и должна быть пересмотрена. CubeTopology должна тестироваться без Renderer2D; Game Engine — без UI; automatic alive/dead/seki — без пользовательского интерфейса; Renderer3D — без изменения Game Engine. Допустимы интеграционные тесты между слоями, но базовая корректность каждого слоя должна доказываться отдельно.

# Renderer Contract и пространственная модель куба

# Renderer Contract вводится уже в 0.1. Renderer получает GameState, ViewState и renderer-neutral данные Topology/render mapping и отвечает только за отображение и преобразование пользовательского взаимодействия в PointId или доменное/UI-намерение. Renderer не определяет соседство, правила, допустимость хода, не создаёт логические PointId и не хранит авторитетную игровую позицию.

# PointId запрещено строить из SVG/CSS/DOM/canvas/Three.js-идентификаторов, пиксельных координат или другой информации конкретного Renderer. Логическая идентичность точки должна переживать полную замену Renderer2D на Renderer3D без изменения GameState и правил.

# Начиная с 0.2 вводится Cube Surface/Spatial Mapping Contract. Для каждой логической точки куба должна существовать каноническая renderer-neutral привязка к поверхности куба — например FaceId \+ локальные координаты u/v или эквивалентная структура. Отдельно задаётся каноническая ориентация каждой грани и согласованные переходы между её сторонами. Конкретный формат может быть выбран при проектировании 0.2, но он не должен зависеть от SVG, CSS transforms, DOM или будущего Three.js.

# Ориентационный якорь между Cube 2D и будущим Cube 3D также хранится в renderer-neutral форме — например FaceId \+ quarterTurns (0/1/2/3) или эквивалент. Renderer2D переводит этот якорь в собственные transform-ы, а Renderer3D позднее переводит те же данные в quaternion/matrix/камеру. Ни svgTransformMatrix, ни Three.js Quaternion не являются каноническим состоянием ориентации проекта.

# Cube 2D в 0.2 не считается архитектурно готовым, пока CubeTopology, CubeOrientation и Cube2DLayout можно полностью проверить headless без SVG, DOM и Renderer2D: PointId → face/local position, ориентации граней, переходы через стороны, round-trip, матрица 3×4, ровно 6 occupied cells и 6 null, уникальность каждой CubeFace, корректные rotation и ровно 6 × N × N visual points без дублей покрываются автоматическими тестами.

# При начале 0.5 Renderer3D должен подключаться как новый адаптер к уже готовым CubeTopology, PointId, spatial mapping и orientation anchor. Если для Three.js/R3F или другой выбранной 3D-библиотеки приходится извлекать пространственную модель из CSS/SVG-кода 0.2 либо менять GameState/правила, это считается архитектурным дефектом предыдущего этапа и требует исправления границы, а не переноса 3D-зависимостей в Game Engine.

# Критерий совместимости с будущими 3D-библиотеками: любую выбранную 3D-библиотеку должно быть возможно заменить другой нормальной 3D-библиотекой, переписав Renderer3D/adapters, но не CubeTopology, GameState, правила, scoring, history или доменные команды.

# Предварительный обзор библиотек и повторного использования

Перед началом программирования каждого крупного этапа проводится короткий Library/Reuse Review. Обязательным является сам обзор доступных решений, а не использование конкретной библиотеки. Цель — не писать собственный код там, где зрелое open-source решение действительно уменьшает объём работы и риски, но и не подчинять архитектуру проекта чужому фреймворку только ради экономии нескольких файлов.

При обзоре нужно проверять не только перечисленные ниже проекты, но и актуальные на момент начала этапа альтернативы. Список кандидатов является отправной точкой и не фиксирует конкретные версии пакетов. Перед реальным подключением повторно проверяются лицензия и требования к атрибуции, активность поддержки, качество тестов, TypeScript/browser-совместимость, размер и runtime-стоимость, стабильность API, архитектурная связанность, риск vendor lock-in, безопасность цепочки зависимостей и стоимость адаптации к TorusTopology/CubeTopology.

Для каждого серьёзного кандидата допустимы четыре результата: использовать как зависимость; адаптировать отдельный код или алгоритм с соблюдением лицензии; использовать только как reference/test oracle; отказаться и написать собственную реализацию. Если зависимость затрагивает Game Engine, Topology, историю, Renderer или будущую сеть, перед окончательным решением рекомендуется небольшой изолированный spike/prototype. Внешняя библиотека не должна становиться источником истины по игровому состоянию и не может нарушать принцип Game Engine ≠ Topology ≠ Renderer.

## 0.1 — Library/Reuse Review

Перед реализацией стандартной логики ГО отдельно исследовать существующие open-source движки и библиотеки. В первую очередь рассмотреть @sabaki/go-board как возможный источник или основу для групп, дыханий, взятий, suicide, ko и анализа хода; online-go/goban и goban-engine — как зрелый reference/test oracle и возможный источник отдельных решений; fast-check — как кандидат для property-based/fuzz-тестирования. Для SGF-инструментов можно рассмотреть @sabaki/sgf, а для идей 2D-goban UI — Shudan, не превращая пользовательский SGF import/export в требование 0.1.  
Главный spike 0.1: проверить, можно ли отделить стандартную Go-логику выбранного проекта от прямоугольных координат и заменить встроенное соседство на наш Topology.neighbors(PointId). Если это удаётся чисто и тестируемо — допускается reuse/adaptation. Если библиотека жёстко привязана к обычной доске, она остаётся reference/test oracle, а собственный topology-independent Game Engine пишется без этой зависимости.

## 0.2 — Library/Reuse Review

CubeTopology остаётся нашей предметной логикой и не подменяется универсальным UI-фреймворком. Для Renderer2D и взаимодействия рассмотреть Shudan как reference/селективный источник решений, а также универсальные 2D-инструменты вроде Konva или PixiJS и сравнить их с уже выбранным React+SVG/собственным рендерером. Решение «не добавлять новую библиотеку» считается полностью допустимым, если она не уменьшает сложность 3×4 slot layout, однозначного visual point → PointId mapping, rotation, навигации, анимаций и визуальных стыков шести уникальных граней.

## 0.3 — Library/Reuse Review

Перед написанием automatic alive/dead/seki обязательно изучить существующие алгоритмы и реализации, в частности @sabaki/deadstones и online-go/score-estimator, а также актуальные альтернативы. Проверить, можно ли перенести алгоритм на абстрактный граф Topology без предположений о прямоугольной доске. Допустимо использовать библиотеку только как источник алгоритмических идей или oracle на обычных позициях. Никакая внешняя оценка не отменяет наше правило: автоматически принимаются только доказуемые/очевидные случаи, всё недоказанное уходит в ручной fallback.

## 0.5 — Library/Reuse Review

Перед Cube 3D сравнить Three.js, @react-three/fiber и актуальные альтернативы. Spike должен проверить как минимум hit-testing до PointId, геометрию плоских граней со скруглёнными стыками, вращение/зум, сохранение пространственного якоря Cube 2D ↔ Cube 3D и отсутствие проникновения 3D-состояния в GameState. Выбирать более высокий уровень абстракции только если он реально уменьшает код без потери контроля над этими требованиями.

## Future Online Multiplayer — Library/Reuse Review

Перед началом сетевой версии заново исследовать актуальные authoritative multiplayer frameworks. В качестве отправных кандидатов рассмотреть boardgame.io и Colyseus, а также текущие альтернативы. Любое решение должно подключаться вокруг уже существующего Game Engine: клиент отправляет намерение/доменные команды, сервер остаётся авторитетным источником истины и повторно валидирует игру. Фреймворк, требующий переписать правила под собственную модель состояния, не получает автоматического преимущества только за наличие готовых lobby/matchmaking/network-функций.

Общее правило test oracle  
Стандартные Go-библиотеки и движки могут использоваться для differential/regression-сравнения на обычных плоских позициях: одинаковая позиция и набор правил должны давать согласованный результат там, где модели совпадают. Такое сравнение повышает доверие к стандартной Go-логике, но не доказывает корректность тора или куба; необычная топология всегда проверяется нашими Topology Contract, fixtures и fuzz-инвариантами.

Общее правило изоляции зависимости  
По возможности внешние библиотеки подключаются через наши узкие интерфейсы/адаптеры. Это позволяет заменить или удалить зависимость без изменения GameState, Topology Contract и публичных доменных команд. При копировании или адаптации стороннего кода сохраняются все обязательные лицензии, notices и атрибуции.

## Обязательный поиск готовых решений ДО планирования версии

Library/Reuse Review проводится не после того, как архитектура и итерации уже придуманы, а до планирования каждой пользовательской версии 0.1, 0.2, 0.3, 0.5 и любой будущей крупной версии. Нельзя сначала спроектировать собственную реализацию, а затем формально проверить библиотеки. Результаты поиска должны влиять на сам план: какие части вообще не нужно писать, какие можно адаптировать, какие использовать как reference/oracle, а какие действительно являются уникальной логикой Game Cube Go.  
До утверждения плана версии нужно искать не только Go-библиотеки, но и общие готовые primitives, frameworks, reference implementations, примеры и небольшие open-source модули по всем применимым подзадачам: state/history, schema validation, persistence, 2D rendering, animation, drag/pan/zoom, hit-testing, geometry, 3D controls, picking, instancing, lines, testing, visual regression, networking и другим стандартным задачам. Приоритет — не «найти один большой framework», а вычленить готовые надёжные кирпичики там, где они реально сокращают код и риск.  
Перед утверждением плана фиксируется короткий Reuse Decision: что искали; какие кандидаты нашли; что можно использовать напрямую; что можно адаптировать; что годится только как reference/test oracle; что отвергнуто и почему; какой код всё равно остаётся нашим. Если подходящего решения нет, это тоже нормальный зафиксированный результат.

## Обязательный повторный поиск ПЕРЕД каждым checkpoint

Даже после общего обзора версии перед началом каждого технического checkpoint проводится короткий целевой поиск именно под его задачи. Например, перед topology-core ищутся готовые graph/topology/test primitives; перед renderer-functional — 2D rendering/interaction/animation решения; перед Renderer3D — geometry/controls/picking/instancing. Это защищает от ситуации, когда подходящее решение было пропущено при общем обзоре или появилось позднее.  
Повторный поиск должен быть соразмерным: не превращать каждый небольшой checkpoint в исследовательский проект, но обязательно проверить зрелые и актуальные варианты до написания заметного объёма собственного низкоуровневого кода.

## Общие кандидаты и primitives, уже найденные к рассмотрению

0.1 / базовый web-stack и инфраструктура: React для UI, Vite для сборки/dev-сервера, Vitest для unit/integration tests, Playwright для E2E и visual screenshot regression, fast-check для property-based/fuzz testing, Zod или актуальный аналог для runtime-валидации GameState/save schema и будущих migrations, Motion для 2D-анимаций. Это кандидаты, а не жёстко утверждённый стек; перед началом 0.1 нужно повторно проверить актуальные альтернативы.  
0.1 / Go-логика: @sabaki/go-board, online-go/goban/goban-engine, @sabaki/sgf и другие решения из уже описанного Library/Reuse Review. Главная цель — переиспользовать стандартную Go-логику без переноса предположения о прямоугольной доске.  
0.2 / Cube 2D: в первую очередь сравнить простой React \+ SVG \+ Motion с react-konva/Konva, PixiJS, Shudan и актуальными аналогами. SVG остаётся сильным кандидатом из-за малого количества объектов и удобного соответствия visual element → PointId; дополнительный canvas/framework нужен только если реально сокращает сложность. Независимо от renderer-технологии Cube 2D должен повторно использовать общий BoardTheme, stone SVG и другие shared visual assets Torus 2D; создание второй самостоятельной темы считается лишним дублированием.  
0.5 / Cube 3D: в первую очередь исследовать Three.js \+ @react-three/fiber \+ Drei и соответствующие готовые primitives. Для базовой формы куба рассмотреть RoundedBoxGeometry вместо собственного генератора mesh; для вращения/zoom — OrbitControls или эквивалент; для mouse picking/hit-testing — Raycaster; для большого числа одинаковых камней — InstancedMesh; для сетки — LineSegments/родственные line primitives. Motion или 3D-native animation helpers можно рассматривать для анимаций. Нашим остаётся отображение PointId на поверхность, ориентация камней, непрерывность сетки через стыки и связь Renderer с CubeTopology.  
future / 3D Torus: стандартный круглый TorusGeometry не считать очевидным решением, потому что описанная нами форма — квадратная объёмная рамка. Первым кандидатом проверить Three.js Shape с внутренним hole \+ ExtrudeGeometry \+ bevel: такая комбинация потенциально даёт верхнюю/нижнюю рамочные поверхности, четыре внешние и четыре внутренние стены без собственного низкоуровневого mesh-generator. CSG-подходы, например актуальный three-bvh-csg или аналоги, рассматривать только как запасной вариант после проверки зрелости и численных рисков.  
future / Online: boardgame.io, Colyseus и актуальные alternatives оцениваются заново перед реальным online-планом; готовые rooms/lobby/reconnect/state sync полезны только при сохранении нашего authoritative Game Engine contract.

## Процессный приоритет reuse

Для стандартной технической задачи по умолчанию сначала ищется готовый зрелый primitive или проверенный open-source код. Собственная реализация выбирается после сравнения, если она действительно проще, безопаснее, лучше соответствует архитектуре или стороннее решение создаёт лишнюю связанность. Для уникальной логики Game Cube Go — CubeTopology, TorusTopology, PointId mapping, topology-independent rules и специфическое поведение интерфейса — сохраняется приоритет собственного контролируемого кода.
